# セキュリティ・障害復旧 60%到達実装計画書

## 1. 文書の目的

高校生向け30分プログラミング体験「みんなの投票で物語を作ろう」を、単一会場・運営PC1台・参加端末最大100台程度の条件で安全に完走できる状態へ引き上げる。

本計画では、企業向けサービスのような完全な防御・高可用性を目指さない。想定される事故や軽度の不正操作を防ぎ、障害発生時にも非技術スタッフを含む運営チームが短時間で通常進行または挙手投票へ復帰できる状態を「完成度60%」と定義する。

今後の計画管理と実装作業は、Codexの「オーキャン」プロジェクト内で行う。コードの対象は同プロジェクト内の `oc26-story` リポジトリとする。

## 2. 前提条件

- 1回30分の単一セッション
- 運営PC1台でNode.jsサーバーを起動
- 参加者、中央モニター、運営者の3画面を使用
- 当日スタッフは主担当1人と、プログラミング未経験に近い補助スタッフ2人
- 参加者の氏名やメールアドレスなどの個人情報は取得しない
- 外部データベースは使用しない
- 通常時はPC投票、障害時は挙手投票へ切り替えられる
- Cloudflare Tunnelまたは学校LAN内からアクセスする

## 3. 想定する脅威と障害

### 対策対象

- 参加者がブラウザの開発者ツールから運営者用APIやSSEを開く
- 参加者IDを書き換えて複数票を投じる
- PINを繰り返し試す
- ボタン連打や通信再送で同じ操作が複数回実行される
- 不正なJSONや過大なリクエストが送信される
- Wi-FiやTunnelが一時的に切断される
- SSE接続が切れたまま古い画面が表示される
- Node.jsプロセスや運営PCが再起動する
- 投票中に複数端末が同時に接続できなくなる
- 非技術スタッフが状況を判断できず、対応が遅れる

### 今回の対象外

- 大規模DDoSへの防御
- 複数サーバーによる自動フェイルオーバー
- 外部IdPや多要素認証
- 高度な不正検知・端末フィンガープリント
- 投票中の個別票を含む完全な永続化
- 長期的な監査ログや開催結果分析
- データベース障害対策

## 4. 60%到達の合格条件

### セキュリティ

以下をすべて満たした時点で、今回の利用条件におけるセキュリティ完成度60%以上と判定する。

- 参加者IDをサーバーが発行し、`HttpOnly` Cookieで保持する
- 投票APIがリクエスト本文の `participantId` を信用しない
- 1つの参加者セッションにつき一票となり、締切までは変更だけを許可する
- PINログイン後に短時間有効な運営者セッションを発行する
- 運営者用API、状態取得、SSEを未認証ユーザーへ返さない
- PIN試行回数に簡易制限を設ける
- 状態変更APIへ同一オリジン確認を入れる
- Cookieへ `HttpOnly`、`SameSite=Strict`、HTTPS時の `Secure` を設定する
- 本番モードで開発用PINを使用している場合、起動警告とready失敗を返す
- 認証・投票・入力検証の自動テストが成功する

### 障害復旧

以下をすべて満たした時点で、障害復旧完成度60%以上と判定する。

- 進行状態をバージョン付きJSONとして保存する
- JSONは一時ファイルへの書き込み後にrenameし、途中破損を防ぐ
- サーバー再起動時に最後の正常な状態を自動復元する
- 投票中・締切後に再起動した場合は、そのラウンドを投票準備状態へ戻す
- 再起動で個別票が失われたことを運営者画面へ明示する
- SSE再接続時に最新スナップショットを必ず再送する
- SSEを利用できない経路ではHTTPポーリングへ自動的に切り替える
- 状態リビジョン番号により、古い更新を画面へ適用しない
- `/health/live` と `/health/ready` を提供する
- 運営者が現在状態をJSONとしてダウンロードできる
- PC投票から挙手投票へ安全に切り替えられる
- 再起動・再接続・破損スナップショットの自動テストが成功する

## 5. 実装方針

### 5.1 匿名参加者セッション

初回アクセス時にサーバーが暗号学的乱数による匿名IDを発行する。

- Cookie名：`oc26_participant`
- 属性：`HttpOnly; SameSite=Strict; Path=/`
- HTTPSまたは `X-Forwarded-Proto: https` の場合は `Secure`
- 有効期間：当日の運用を十分に含む12時間
- 氏名、IPアドレス、User-Agentは投票データへ保存しない
- クライアントから送信された参加者IDは無視する

追加・変更API：

| メソッド | パス | 内容 |
| --- | --- | --- |
| `POST` | `/api/participants/session` | 匿名参加者Cookieを発行 |
| `PUT` | `/api/vote` | Cookieに対応する一票を登録・変更 |
| `GET` | `/api/state?role=participant` | 自分の選択状態を含む参加者向け状態 |

### 5.2 運営者セッション

生のPINをすべての操作で送信する方式を廃止する。

- `POST /api/operator/login` でPINを確認
- 比較には `crypto.timingSafeEqual` を使用
- ログイン成功時にランダムなセッショントークンを発行
- Cookie名：`oc26_operator`
- 有効期間：2時間。操作時に延長しない
- セッションはサーバーメモリに保持し、再起動時は再ログインする
- `POST /api/operator/logout` で破棄
- 運営者API、運営者状態、運営者SSEは有効なセッションを必須とする

PIN試行制限：

- 接続元ごとに5回失敗したら5分間拒否
- 成功時は失敗回数をリセット
- 失敗理由は「PINが違います」に統一し、内部状態を明かさない

### 5.3 役割別アクセス制御

既存の状態投影に認証境界を追加する。

- `participant`：匿名参加者Cookieを利用。票数・確率・運営設定は返さない
- `display`：会場表示に必要な公開情報を返す
- `operator`：有効な運営者セッションがある場合だけ全状態を返す
- `support`：票数やPINを含まない運用情報だけを返す
- 不正なroleは `400`、認証不足は `401`、権限不足は `403`

### 5.4 最小限の入力・リクエスト防御

- JSON本文は64KB以下
- `Content-Type: application/json` を必須化
- 選択肢ID、β、投票方式、挙手数をallow-listで検証
- 状態変更APIでは `Origin` と `Host` の一致を確認
- 一参加者セッションあたり投票APIを1分30回までに制限
- 運営操作は処理中に同一ボタンを無効化する
- APIエラーを `{ error: { code, message } }` へ統一する

## 6. 障害復旧設計

### 6.1 保存する状態

`data/session-state.json` に以下だけを保存する。

```json
{
  "schemaVersion": 1,
  "storyId": "school-mystery-demo",
  "revision": 12,
  "phase": "round-ready",
  "currentNodeId": "round-2-envelope",
  "history": [],
  "beta": 1,
  "mode": "online",
  "lastDraw": null,
  "updatedAt": "2026-08-20T00:00:00.000Z"
}
```

個別のオンライン投票は保存しない。投票途中または締切後に再起動した場合、該当ラウンドを `round-ready` へ戻し、再投票を行う。これにより部分的な票だけで抽選する事故を防ぐ。

### 6.2 保存タイミング

- 運営操作が正常終了した直後
- 抽選結果が確定した直後
- βまたは投票方式を変更した直後
- 正常終了シグナル受信時

投票1件ごとのディスク書き込みは行わない。

### 6.3 原子的保存と復元

- `session-state.tmp` へ書き込む
- 書き込み完了後に `session-state.json` へrename
- 現在ファイルを `session-state.previous.json` として1世代保持
- 起動時にschemaVersion、storyId、ノードID、フェーズを検証
- 現在ファイルが破損していれば前世代を試す
- 両方が無効なら初期状態で起動し、運営者画面へ警告する

### 6.4 SSE再接続

- 全状態変更に単調増加する `revision` を付与
- SSEへ `id: <revision>` を付ける
- 新規接続・再接続時は差分ではなく最新状態を送る
- クライアントは保持中のrevisionより古い状態を無視する
- 15秒ごとにheartbeatを送る
- 切断時は接続一覧から確実に削除する
- 画面は「接続済み／再接続中／接続できません」を表示する

### 6.5 ヘルスチェック

| パス | 成功条件 |
| --- | --- |
| `/health/live` | Node.jsプロセスが応答できる |
| `/health/ready` | 物語データ、保存先、PIN設定、現在状態が有効 |

readyが失敗してもプロセスは停止させず、運営者画面とサポート画面へ理由を日本語で表示する。

## 7. 非技術スタッフ向け運用支援

### 7.1 参加者画面

- 接続状態を色と文章で表示
- 再接続は自動実行
- 10秒以上復帰しない場合は「ページを再読み込みしてください」と表示
- 投票済み、変更済み、締切済みを明確に区別
- エラー時は技術用語ではなく、次に行う操作を表示
- スタッフへ伝える短いエラー番号を表示

### 7.2 `/support` 画面

補助スタッフがスマートフォンから確認できる読み取り専用画面を追加する。

- サーバー状態
- 現在フェーズ
- 接続端末数
- 参加者用URL
- 現在の投票方式
- 状況別の対応手順
- 「複数端末で赤表示なら主担当を呼ぶ」などの判断基準

票数、抽選確率、PIN、リセット操作は表示しない。

### 7.3 緊急時の固定手順

| 状況 | 補助スタッフ | 主担当 |
| --- | --- | --- |
| 1台だけ接続できない | URLを開き直し、再読み込み | 対応不要 |
| 数台で再接続中 | 10秒待機後に再読み込み | 接続台数を確認 |
| 多数の端末が接続不可 | 参加者へ待機案内 | 挙手投票へ切り替え |
| サーバー再起動 | 参加者へその場で待機案内 | 復元表示を確認し、そのラウンドを再投票 |
| 投票済みか不明 | 参加者画面の「投票済み」を確認 | 必要なら再投票を案内 |

### 7.4 スタッフ用資料

- `docs/staff-quick-guide.md` を作成
- A4一枚に収まる内容とする
- 緑・黄・赤の意味、再読み込み、主担当を呼ぶ条件を記載
- PINやサーバーコマンドは補助スタッフ資料へ載せない

## 9. 自動テスト計画

### セキュリティ

- Cookie未発行時に投票セッションを作成できる
- 同じCookieの再投票が票の追加ではなく変更になる
- 本文中の偽participantIdが無視される
- 未認証の運営者API・状態・SSEが拒否される
- 正しいPINでログインできる
- 誤PIN連続試行が制限される
- 期限切れ運営者セッションが拒否される
- 期限切れの既存運営者SSEもサーバー側から終了する
- 不正Originと過大JSONが拒否される
- 同じ状態番号の運営操作を二重送信しても一度しか進行しない
- 本番環境で開発用PINを使用するとreadyにならない

### 復旧

- 正常スナップショットから復元できる
- 強制停止後はサーバー世代を識別し、参加者セッションを自動再発行できる
- 保存先へ書き込めない場合はreadyにならない
- 現在・前世代の両方が破損した場合に画面警告し、正常保存後にreadyへ戻る
- 投票中の再起動で `round-ready` へ戻る
- 破損ファイルから前世代へ復元できる
- 両方破損時に初期状態で起動する
- storyId不一致を拒否する
- 最新revisionだけが画面へ適用される

### 運用

- `/health/live` と `/health/ready` の成功・失敗条件
- `/support` に非公開票数やPINが含まれない
- PC投票から挙手投票への切り替え確認
- 二重操作が一度だけ実行される

## 11. 完了時の到達状態

本計画完了後は次の状態となる。

- 参加者が簡単な操作で多重投票や運営者情報取得を行えない
- 運営者権限が短時間セッションで保護される
- 通信切断後に自動で最新状態へ戻れる
- サーバー再起動後も物語の進行履歴を復元できる
- 投票中の障害は、そのラウンドだけ再投票することで安全に復帰できる
- 非技術スタッフが画面の色と文章に従って参加者を支援できる
- 復旧不能時にも挙手投票へ移行し、30分体験を完走できる

これを本企画におけるセキュリティ・障害復旧完成度60%の合格ラインとする。
