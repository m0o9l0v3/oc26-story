# バックエンド開発計画

> セキュリティ・障害復旧を本企画の合格ラインである60%まで引き上げる具体的な実装範囲は、[セキュリティ・障害復旧 60%到達実装計画](security-recovery-60-plan.md)を参照する。

## 1. 目標

高校生向け30分体験を、1台の運営PCから安全かつ安定して進行できるバックエンドにする。

- 参加者は一端末一票で、締切までは選択を変更できる
- 中央モニターはリアルタイムに集計を表示できる
- 運営者だけが開始・締切・抽選・リセットを実行できる
- 通信が一時的に切れても、自動再接続して最新状態へ戻れる
- 参加者へ投票途中の票数や抽選確率を送らない
- 氏名、メールアドレスなどの個人情報は保存しない

## 2. v1の構成方針

v1は、Node.js 20の単一プロセスを「その回の体験の正しい状態を持つ場所」とする。30分の単一会場イベントでは、外部データベースや複数サーバーを先に導入するより、構成を小さく保つ方が障害点を減らせる。

```text
参加者ブラウザ ─┐
中央モニター ──┼─ HTTPS / SSE ─ Node.js運営サーバー ─ 物語データ
運営者ブラウザ ─┘                         └─ 任意の復旧用スナップショット
```

複数教室の同時開催、履歴分析、複数サーバー構成が必要になった時点でSQLiteまたはPostgreSQLへ移行する。セッション処理をHTTP処理から分離しておき、保存方式を後から交換できる構造にする。

## 3. 重要課題と進捗

### 最優先：役割ごとの状態分離

2026年8月20日にB1の役割別状態投影を実装した。参加者向けAPIとSSEは許可項目だけを返し、票数・確率・抽選結果・運営設定を返さない。中央モニターと運営者は、現在の表示と操作に必要な集計状態を受け取る。

返却データは次の3種類に分ける。

| 役割 | 受け取れる情報 |
| --- | --- |
| 参加者 | フェーズ、設問、選択肢、自分の選択状態 |
| 中央モニター | フェーズ、設問、接続台数、公開可能になった集計結果 |
| 運営者 | 全状態、リアルタイム票数、抽選設定、復旧情報 |

投票中の票数は運営者だけに返し、中央モニターには現在の仕様に合わせて必要な範囲だけ公開する。参加者には常に返さない。

### 参加者IDをブラウザ申告だけにしない

現在はブラウザが送った `participantId` をそのまま信用している。v1では最初の接続時にサーバーが匿名IDを発行し、`HttpOnly` Cookieで保持する。投票APIはリクエスト本文のIDではなくCookieを使用する。

### 運営者認証を短時間セッション化する

PINを毎回APIへ送る方式から、PIN確認後に短時間だけ有効な運営者セッションを発行する方式へ移行する。PIN試行回数にも簡易制限を設ける。

## 4. 目標モジュール構成

```text
src/
  domain/
    story-session.js       進行状態と投票・抽選ルール
    probability.js         確率計算と抽選
  application/
    commands.js            運営操作の実行
    state-projections.js    役割別に返却データを生成
  transport/
    http-server.js          HTTPルーティング
    sse-hub.js              SSE接続・再接続・配信
    cookies.js              匿名参加者と運営者セッション
  infrastructure/
    snapshot-store.js       任意の復旧用保存
  story-data.js
  server.js                 起動処理だけを担当
```

HTTP、進行ルール、保存処理を分離し、テスト時にはブラウザや実際のネットワークなしでルールを確認できるようにする。

## 5. APIの目標形

| メソッド | パス | 用途 |
| --- | --- | --- |
| `POST` | `/api/participants/session` | 匿名参加者Cookieを発行 |
| `GET` | `/api/state?role=participant` | 参加者向け状態 |
| `GET` | `/api/state?role=display` | 中央モニター向け状態 |
| `GET` | `/api/events?role=...` | 役割別SSE |
| `PUT` | `/api/vote` | 自分の一票を登録・変更 |
| `POST` | `/api/operator/login` | PINを確認して運営者セッションを発行 |
| `POST` | `/api/operator/actions` | 認証済み運営操作 |
| `GET` | `/health/live` | プロセス生存確認 |
| `GET` | `/health/ready` | 開催可能状態の確認 |

APIエラーは、画面に表示する日本語とは別に、コードでも判別できる形式へ統一する。

```json
{
  "error": {
    "code": "VOTING_CLOSED",
    "message": "投票は締め切られています"
  }
}
```

## 6. 開発フェーズ

### B1：境界と情報漏えい対策

状態：役割別投影とAPI・SSE分離まで完了（エラー形式の統一はB2で継続）。

- 役割別の状態投影を実装
- 参加者向けレスポンスから票数・確率・抽選結果の未公開情報を除外
- 運営者操作のテストを役割別に追加
- APIエラー形式を統一

完了条件：参加者APIとSSEのレスポンスに非公開集計が一切含まれない。

### B2：匿名参加者・運営者認証

- サーバー発行の匿名参加者Cookie
- PINログインと短時間の運営者セッション
- PIN試行回数の簡易制限
- Cookieの `HttpOnly`、`SameSite=Strict`、HTTPS時の `Secure`

完了条件：リクエスト本文の参加者IDや生のPINに依存せず投票・運営操作ができる。

### B3：リアルタイム通信の強化

- SSEメッセージに単調増加するリビジョン番号を付与
- 再接続時に必ず最新スナップショットを送信
- 切断済み接続の確実な破棄
- 遅いクライアントへのバックプレッシャー対策
- 参加者、投影、運営者ごとの配信内容を分離

完了条件：Wi-Fiを一時的に切断して戻しても、画面更新なしで正しい状態へ復帰する。

### B4：復旧と運用

- フェーズ、現在ノード、履歴、設定だけを原子的にJSON保存
- 投票中の匿名票を保存するかは本番リハーサル後に決定
- 起動時のスナップショット復元
- ヘルスチェックと構造化ログ
- 誤操作時の状態エクスポート

完了条件：運営サーバーを再起動しても、直前のラウンドから再開できる。

### B5：負荷・障害試験

- 参加端末100台相当のSSE接続試験
- 同時投票、投票変更、締切直前投票の競合試験
- 切断・再接続の反復試験
- Cloudflare Tunnel経由と学校LAN内の両方でリハーサル
- 挙手投票への切り替え手順を確認

完了条件：想定最大人数の2倍で進行不能、重複集計、メモリ増加が発生しない。

## 7. データベースを追加する条件

次のどれかが必要になった場合にSQLiteを導入する。

- 複数教室で同時に別の物語を進行する
- 過去の開催結果を集計する
- サーバー再起動後も投票を完全復元する
- 複数の運営PCから同じセッションを操作する

単一会場・単一セッションのv1では、外部DBは導入しない。個人情報を集めない方針も維持する。

## 8. 直近の実装順

1. `state-projections.js` を追加し、参加者への集計情報漏えいを修正
2. 運営者画面の操作フローに合わせてコマンドAPIを整理
3. 匿名参加者Cookieを導入
4. SSEのリビジョン番号と再接続テストを追加
5. 復旧用スナップショットを追加
6. 100台相当の負荷試験を実施

最初のバックエンド実装単位はB1とし、運営者画面の実装と同じブランチ上でAPI契約を確定する。
